## 라. 클라우드 기반 AIoT 서비스 플랫폼 배포
### 1) Docker, K8S 기본 개념
#### Slide - 컨테이너 기술의 이해 - Docker, Docker Compose, Kubernetes

🐳 Docker (도커)
"단일 컨테이너 실행"
- 하나의 애플리케이션을 컨테이너로 실행
- 기본 빌딩 블록

🎼 Docker Compose (도커 컴포즈)
"여러 컨테이너 관리"
- YAML 파일로 다중 컨테이너 정의
- 한 서버에서 여러 서비스 연동
- 사용 예: 웹서버 + DB + 캐시를 함께 실행

☸️ Kubernetes (쿠버네티스)
"대규모 컨테이너 오케스트레이션"
- 여러 서버에 걸친 자동화된 컨테이너 관리
- 자동 확장, 복구, 로드밸런싱
- 사용 예: 수백 개 컨테이너를 운영하는 프로덕션 환경

``` 스크립트
슬라이드 설명 (약 3-4분)
자, 이제 본격적으로 도커, 도커 컴포즈, 쿠버네티스가 뭔지 알아볼게요. 왼쪽부터 하나씩 살펴보죠.
🐳 도커 (Docker)
먼저 도커입니다. 도커는 **"단일 컨테이너 실행"**이라고 생각하시면 돼요.
쉽게 말해서, 하나의 애플리케이션을 컨테이너라는 상자에 담아서 실행하는 거예요. 여기서 중요한 건, 도커가 바로 모든 컨테이너 기술의 기본 빌딩 블록이라는 거죠. 레고로 치면 기본 블록 하나하나라고 생각하시면 됩니다.
예를 들어볼게요. 여러분이 Node.js로 만든 웹 애플리케이션이 하나 있다고 해봅시다. 이걸 도커 컨테이너로 만들면, 어디서든 똑같이 실행할 수 있어요. 내 컴퓨터에서도, 팀원 컴퓨터에서도, 서버에서도 말이죠. 환경 차이로 생기는 문제가 사라지는 거예요.
🎼 도커 컴포즈 (Docker Compose)
그 다음이 도커 컴포즈인데요, 이건 **"여러 컨테이너를 관리"**하는 도구예요.
실제로 서비스를 만들다 보면, 애플리케이션 하나만 있으면 안 되잖아요? 웹 서버도 필요하고, 데이터베이스도 필요하고, 캐시 서버도 필요할 수 있죠. 이렇게 여러 개의 컨테이너를 한꺼번에 관리해야 할 때 도커 컴포즈를 사용해요.
도커 컴포즈는 YAML이라는 파일 형식으로 컨테이너들을 정의합니다. 그러니까 설정 파일 하나에다가 "웹서버는 이렇게, 데이터베이스는 저렇게" 쭉 적어놓는 거예요. 그럼 한 서버 안에서 여러 서비스들이 서로 연동되면서 돌아가게 되는 거죠.
구체적인 예를 들면, 웹서버 하나, PostgreSQL 데이터베이스 하나, Redis 캐시 서버 하나, 이렇게 세 개를 함께 실행하고 싶을 때 도커 컴포즈를 쓰면 명령어 하나로 전부 띄울 수 있어요. 엄청 편하죠?
☸️ 쿠버네티스 (Kubernetes)
마지막으로 쿠버네티스인데요, 이건 좀 다른 차원이에요. **"대규모 컨테이너 오케스트레이션"**이라고 하는데, 오케스트레이션이 뭐냐면 오케스트라 지휘하듯이 여러 개를 조율한다는 뜻이에요.
쿠버네티스는 여러 서버에 걸쳐서 수많은 컨테이너들을 자동으로 관리해줘요. 예를 들어 컨테이너 하나가 죽으면? 자동으로 다시 살려줍니다. 이게 바로 자동 복구 기능이에요. 트래픽이 갑자기 늘어나서 서버가 더 필요하면? 자동으로 컨테이너를 늘려줘요. 이게 자동 확장이고요. 그리고 로드밸런싱이라고 해서 트래픽을 여러 컨테이너에 골고루 분산시켜주는 것도 자동으로 해줍니다.
실제로 대기업이나 큰 서비스에서는 컨테이너가 수백 개, 수천 개씩 돌아가거든요. 이걸 사람이 일일이 관리할 수는 없잖아요? 그래서 쿠버네티스 같은 도구가 필요한 거예요. 프로덕션 환경, 그러니까 실제 사용자들이 쓰는 운영 환경에서 많이 사용합니다.

📊 비교표로 정리하면
자, 이제 오른쪽 표를 한번 볼까요? 세 가지를 비교해서 정리해놨어요.
관리 단위를 보시면, 도커는 단일 컨테이너 하나만, 도커 컴포즈는 여러 컨테이너인데 한 대의 서버 안에서만, 쿠버네티스는 여러 서버를 묶은 클러스터 전체를 관리합니다.
복잡도는 당연히 도커가 제일 쉽고, 쿠버네티스로 갈수록 어려워져요. 도커는 별 하나, 도커 컴포즈는 별 두 개, 쿠버네티스는 별 세 개 정도의 난이도라고 보시면 됩니다.
적용 대상을 보면, 도커는 주로 개발하거나 테스트할 때 많이 쓰고요, 도커 컴포즈는 소규모 서비스에 적합해요. 쿠버네티스는 대규모 프로덕션, 그러니까 진짜 사용자들이 쓰는 본격적인 서비스에서 사용합니다.
그리고 중요한 차이가 자동 확장하고 자동 복구 기능인데요, 도커랑 도커 컴포즈는 이 기능이 없어요. 엑스 표시 되어 있죠? 근데 쿠버네티스만 체크 표시가 되어 있어요. 이게 바로 쿠버네티스의 핵심 기능이에요. 자동으로 알아서 서버를 늘렸다 줄였다 하고, 문제 생기면 알아서 고쳐주는 거죠.

마무리 멘트:
정리하자면, 도커는 기본, 도커 컴포즈는 여러 개 묶어서 쓰는 것, 쿠버네티스는 대규모로 자동화해서 관리하는 것이라고 기억하시면 됩니다. 처음에는 도커부터 시작하시고, 나중에 필요할 때 도커 컴포즈, 그리고 정말 큰 서비스를 만들게 되면 쿠버네티스를 공부하시면 됩니다.
```

#### Slide - Docker 기본 개념

Docker 주요 개념
- 컨테이너(Container)
	- 독립된 실행 환경 제공, 앱과 필요한 라이브러리를 포함
	- VM과 달리 가벼우며, 시스템 자원을 효율적으로 사용
- 이미지(Image)
	- 컨테이너를 생성하기 위한 템플릿.
	- 애플리케이션의 실행 환경과 필요한 파일, 설정 등을 포함
- Dockerfile
	- 이미지를 생성에 필요한 명령어를 정의한 설정 파일
- Docker Hub
	- Docker 이미지를 공유하고 배포할 수 있는 중앙 저장소
	- 다양한 공개 이미지 제공, 사용자 정의 이미지 업로드 가능
- 볼륨(Volume)
	- 컨테이너와 호스트 시스템 간의 데이터 공유 방법
	- 컨테이너가 종료되어도 볼륨 데이터는 유지됨

``` 스크립트
자, 이제 도커의 핵심 개념들을 좀 더 자세히 알아볼게요. 다섯 가지만 알아두시면 됩니다.
컨테이너 (Container)
먼저 컨테이너인데요, 아까 계속 얘기했던 그 컨테이너 맞아요. 실행 중인 프로그램이라고 생각하시면 돼요. 독립된 실행 환경을 제공하는 거죠. 쉽게 말하면, 앱이랑 그 앱이 돌아가는 데 필요한 모든 라이브러리를 포함하고 있어요.
여기서 중요한 게, 가상머신(VM)이랑 비슷해 보이지만 훨씬 가볍다는 거예요. 가상머신은 무겁고 느린데, 컨테이너는 빠르고 시스템 자원도 효율적으로 사용합니다.
이미지 (Image)
그럼 컨테이너는 어떻게 만드느냐? 바로 이미지로 만들어요. 이미지는 프로그램 설치 파일이라고 생각하시면 딱 맞아요. 윈도우에서 .exe 파일, 맥에서 .dmg 파일 있잖아요? 그런 거예요.
이미지 안에는 애플리케이션 실행 환경, 필요한 파일들, 각종 설정들이 다 들어있어요. 크롬 설치 파일 하나로 크롬을 여러 번 설치할 수 있듯이, 이미지 하나로 컨테이너를 여러 개 실행할 수 있는 거죠.
Dockerfile
그럼 이 이미지는 또 어떻게 만드느냐? Dockerfile이라는 걸로 만들어요. Dockerfile은 프로그램 소스 코드에다가 빌드 스크립트를 합쳐놓은 것이라고 보시면 돼요.
"이 운영체제 깔고, 이 프로그램 설치하고, 이 파일 복사하고" 이런 명령어들을 쭉 적어놓은 설정 파일이에요. 이 파일만 있으면 누구나 똑같은 이미지를 만들어낼 수 있죠. 정리하면, Dockerfile로 이미지를 빌드하고, 그 이미지로 컨테이너를 실행하는 거예요.
Docker Hub
Docker Hub는 도커 이미지를 공유하는 중앙 저장소예요. 앱스토어나 구글 플레이스토어처럼, 프로그램 설치 파일들을 모아둔 곳이라고 생각하시면 됩니다.
여기 가면 엄청나게 많은 공개 이미지들이 있어요. 예를 들어 PostgreSQL 데이터베이스가 필요하면, 직접 Dockerfile 작성하고 빌드할 필요 없이 Docker Hub에서 공식 이미지 받아서 바로 실행하면 돼요. 물론 여러분이 만든 이미지를 올려서 다른 사람들과 공유할 수도 있고요.
볼륨 (Volume)
마지막으로 볼륨이에요. 이건 데이터 저장과 관련된 건데요, 컨테이너는 기본적으로 삭제하면 안에 있던 데이터도 다 사라져요. 프로그램 삭제하면 그 프로그램이 만든 파일들도 사라지는 것처럼요. 근데 데이터베이스처럼 데이터를 계속 보관해야 하는 경우가 있잖아요?
그럴 때 볼륨을 사용하면, 컨테이너와 실제 컴퓨터(호스트 시스템) 사이에서 데이터를 공유할 수 있어요. 컨테이너가 종료되거나 삭제되어도 볼륨에 저장된 데이터는 그대로 남아있습니다. 외장하드에 백업해두는 것처럼 안전하게 데이터를 보관할 수 있는 거죠.
연결 멘트:
자, 정리해볼까요? Dockerfile은 소스 코드와 빌드 방법, Image는 설치 파일, Container는 실행 중인 프로그램, Docker Hub는 앱스토어, Volume은 데이터 저장소. 이 개념들만 확실히 이해하시면 도커 사용하는 데 문제없으실 거예요.
```

#### Slide - K8S 기본 개념

Kubernetes (K8S) 주요 개념 (1/2)
- 노드(Node)
	- Kubernetes 클러스터에서 컨테이너를 실행하는 서버
	- 마스터 노드와 워커 노드로 구성

- 클러스터(Cluster)
	- 여러 노드로 구성된 그룹
	- 애플리케이션을 효율적으로 관리하고 확장 가능하게 함

- 파드(Pod)
	- 하나 이상의 컨테이너를 포함하는 기본 실행 단위
	- 동일한 네트워크와 스토리지 공유

``` 스크립트
자, 이제 쿠버네티스의 핵심 개념들을 알아볼게요. 처음에는 용어가 좀 생소할 수 있는데, 하나씩 차근차근 설명드릴게요.
노드 (Node)
먼저 노드예요. 노드는 쿠버네티스 클러스터에서 실제로 컨테이너가 돌아가는 서버라고 보시면 됩니다. 컴퓨터 한 대라고 생각하시면 쉬워요.
노드는 두 종류가 있어요. 마스터 노드는 전체를 관리하는 관리자 역할이고, 워커 노드는 실제로 일하는 직원들이에요. 워커 노드들이 컨테이너를 실행하면, 마스터 노드가 "너는 이거 해, 너는 저거 해" 하면서 지시하는 거죠.
클러스터 (Cluster)
클러스터는 이런 노드들을 여러 개 묶어놓은 그룹이에요. 회사로 치면 한 팀이라고 볼 수 있죠. 여러 대의 서버를 하나로 묶어서 관리하는 거예요.
왜 여러 대를 묶느냐? 애플리케이션을 효율적으로 관리하고 쉽게 확장할 수 있거든요. 서버 한 대가 고장나도 다른 서버들이 있으니까 서비스가 중단되지 않고요, 트래픽이 많아지면 서버를 더 추가하면 되니까요.
파드 (Pod)
파드는 쿠버네티스에서 가장 작은 실행 단위예요. 하나 이상의 컨테이너를 포함하고 있어요.
여기서 중요한 게, 도커에서는 컨테이너 단위로 관리했다면, 쿠버네티스에서는 파드 단위로 관리한다는 거예요. 보통은 파드 하나에 컨테이너 하나가 들어가지만, 때로는 여러 개가 들어갈 수도 있어요. 같은 파드 안에 있는 컨테이너들은 네트워크랑 스토리지를 공유해서 서로 쉽게 통신할 수 있어요.
```

#### Slide - K8S 기본 개념

Kubernetes (K8S) 주요 개념 (2/2)
- 서비스(Service)
	- 파드에 대한 네트워크 접근을 제공
	- 로드 밸런싱을 통해 트래픽을 분산

- 디플로이먼트(Deployment)
	- 파드의 배포 및 업데이트를 관리
	- 선언적 구성을 통해 원하는 상태를 정의하고 유지

- 네임스페이스(Namespace)
	- 리소스를 논리적으로 분리하여 관리
	- 여러 팀이나 프로젝트가 하나의 클러스터를 공유할 때 유용

``` 스크립트
계속해서 나머지 개념들도 알아볼게요.
서비스 (Service)
서비스는 파드에 접근할 수 있게 해주는 네트워크 통로예요.
파드는 생성되고 삭제되는 게 반복되잖아요? 그럼 IP 주소가 계속 바뀌어요. 그럼 어떻게 접속하냐? 바로 서비스를 통해서 접속하는 거예요. 서비스는 고정된 주소를 제공해서, 파드가 바뀌어도 사용자는 같은 주소로 접속할 수 있어요.
그리고 서비스는 로드 밸런싱 기능도 제공해요. 같은 애플리케이션을 실행하는 파드가 여러 개 있으면, 서비스가 자동으로 트래픽을 골고루 분산시켜줍니다.
디플로이먼트 (Deployment)
디플로이먼트는 파드의 배포와 업데이트를 관리하는 거예요.
쿠버네티스의 핵심 철학이 선언적 구성인데요, "현재 상태"가 아니라 "원하는 상태"를 정의하는 거예요. 예를 들어 "이 애플리케이션 파드를 3개 실행해줘"라고 선언하면, 쿠버네티스가 알아서 3개를 유지해줘요. 파드 하나가 죽으면 자동으로 새로 만들어서 3개를 맞춰주는 거죠.
그리고 무중단 배포도 가능해요. 새 버전으로 업데이트할 때 기존 파드를 하나씩 새 버전으로 교체해서 서비스 중단 없이 업데이트할 수 있어요.
네임스페이스 (Namespace)
마지막으로 네임스페이스인데요, 이건 리소스를 논리적으로 분리하는 거예요.
한 클러스터 안에서 개발팀, 운영팀, QA팀이 각자 작업할 때, 네임스페이스로 공간을 나눠서 쓸 수 있어요. "개발용 네임스페이스", "운영용 네임스페이스" 이런 식으로요. 그럼 서로 간섭하지 않고 독립적으로 작업할 수 있죠. 아파트에서 각 호수가 분리되어 있는 것처럼요.

마무리 멘트:
정리하면, 노드는 서버, 클러스터는 서버들의 그룹, 파드는 실행 단위, 서비스는 네트워크 통로, 디플로이먼트는 배포 관리자, 네임스페이스는 공간 분리 도구예요. 이 여섯 가지만 이해하시면 쿠버네티스의 기본은 다 아신 거예요!
```
