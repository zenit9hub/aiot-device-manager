## 나. 클라우드 기반 AIoT 서비스 플랫폼 설계
### 1) 인프라 구조 설계
#### Slide - 인프라 구조 설계
🔹 인프라 설계 프로세스

1️⃣  요구사항 정의
성능, 보안, 확장성, 비용, 가용성 기준 정리

2️⃣  아키텍처 방향 결정
클라우드/온프레미스, 단일/다중 리전, 컨테이너/서버리스 구조 결정

3️⃣  핵심 구성 요소 선정
컴퓨팅, 데이터베이스, 네트워크, 스토리지, 보안 요소 선정

4️⃣  운영 및 보호 체계 설계
모니터링, 백업, 장애 대응, 접근 제어, 규정 준수 방안 정리

``` 스크립트
이번 장에서는 AIoT 서비스 플랫폼의 인프라 구조를 어떻게 설계할지 살펴보겠습니다.
인프라 설계는 서버를 배치하는 작업이 아니라, 서비스가 안정적으로 운영되고 확장될 수 있는 기반을 정하는 과정입니다.

순서는 크게 네 단계로 보시면 됩니다.
먼저 요구사항을 정리하고, 그 요구사항에 맞는 아키텍처 방향을 결정합니다.
그 다음 핵심 구성 요소를 선택하고, 마지막으로 보안, 모니터링, 백업, 장애 대응까지 포함한 운영 체계를 설계합니다.

정리하면, 인프라 구조 설계는 기술 선택 자체보다도 서비스 목적과 운영 조건에 맞는 균형점을 찾는 과정입니다.
다음 슬라이드에서는 이때 특히 중요하게 봐야 할 고려사항을 정리하겠습니다.
```
---
#### Slide - 인프라 설계 주요 고려사항
🔹 인프라 설계 주요 고려사항

1️⃣  성능 최적화
응답 속도와 처리량 안정적 확보

2️⃣  확장성
사용자 증가와 데이터 증가에 따른 유연한 확장

3️⃣  보안
네트워크, 접근 권한, 데이터 보호 체계

4️⃣  비용 효율성
클라우드 요금제 최적화, 스팟 인스턴스 활용

5️⃣  안정성 및 가용성
장애 발생 시에도 서비스가 지속될 수 있도록 이중화, 복구 전략

``` 스크립트
인프라 설계는 좋은 기술을 많이 넣는 것이 아니라, 성능, 보안, 비용, 운영성을 균형 있게 맞추는 작업입니다.

잘못된 설계는 운영 비용 증가, 성능 저하, 보안 취약점 발생 등의 문제를 초래할 수 있습니다.
따라서 아래 다섯 가지 핵심 고려 사항을 중심으로 인프라 구조를 설계하는 것이 중요합니다.

먼저 성능은 현재 요구사항을 만족해야 하고, 확장성은 앞으로의 성장까지 감당할 수 있어야 합니다.
보안은 설계 후반에 붙이는 것이 아니라 처음부터 네트워크와 권한 구조 안에 포함되어야 합니다.
또한 클라우드 환경에서는 비용 효율성도 매우 중요하며, 마지막으로 안정성과 가용성이 확보되어야 실제 서비스 운영이 가능합니다.

🔹 인프라 설계 시 고려해야 할 5가지 핵심 요소
📌 1️⃣ 성능 최적화 (Performance Optimization)
인프라가 최적의 성능을 발휘할 수 있도록 리소스 사용 최적화, 캐싱, 로드 밸런싱 등의 기술을 적용해야 합니다.
CPU, RAM, 네트워크 대역폭 활용을 최적화하여 처리 속도를 높이고 지연 시간을 최소화해야 합니다.
**캐싱 전략 (Redis, Memcached)**을 적용하면 반복적인 데이터 요청 부담을 줄일 수 있으며,
**로드 밸런서(ALB, Nginx)**를 활용하면 트래픽을 효율적으로 분산할 수 있습니다.
📌 2️⃣ 확장성 (Scalability)
트래픽이 증가하더라도 시스템이 원활하게 확장될 수 있도록 설계해야 합니다.
**오토스케일링(Auto Scaling)**을 적용하면 트래픽에 따라 인프라를 자동으로 확장하거나 축소할 수 있습니다.
**마이크로서비스 아키텍처(MSA)**를 적용하면 개별 서비스 단위로 독립적인 확장이 가능해져 운영이 유연해집니다.
📌 3️⃣ 보안 강화 (Security Enhancement)
인프라 보안은 시스템 보호를 위해 가장 중요한 요소 중 하나입니다.
**네트워크 격리(VPC, 서브넷 분리)**를 통해 내부 시스템을 외부로부터 보호해야 합니다.
**IAM 정책(Identity & Access Management)**을 활용하여 최소 권한 원칙(Least Privilege)을 적용해야 합니다.
DDoS 공격 방어(WAF, AWS Shield) 같은 보안 솔루션을 적용하여 서비스 안정성을 높여야 합니다.
📌 4️⃣ 비용 효율성 (Cost Efficiency)
클라우드 비용 최적화 전략을 적용하여 불필요한 지출을 최소화해야 합니다.
**스팟 인스턴스(AWS EC2 Spot, GCP Preemptible VM)**를 활용하면 일정 수준의 가용성을 유지하면서도 비용을 절감할 수 있습니다.
필요하지 않은 리소스를 자동 종료하는 비용 절감 스케줄링을 활용하는 것도 좋은 방법입니다.
📌 5️⃣ 안정성 및 가용성 (High Availability & Reliability)
시스템이 중단 없이 운영될 수 있도록 이중화, 장애 복구, 무중단 운영 전략을 마련해야 합니다.
**이중화(Redundancy, Multi-AZ 배포)**를 통해 단일 장애점(SPOF, Single Point of Failure)을 제거해야 합니다.
재해 복구(DR: Disaster Recovery) 전략을 수립하여 예상치 못한 장애에 대비해야 합니다.
**무중단 배포(Blue-Green Deployment, Canary Release)**를 활용하면 서비스 중단 없이 지속적인 운영이 가능합니다.


즉, 인프라 설계의 핵심은 이 다섯 요소를 따로 보는 것이 아니라 함께 조정하는 데 있습니다.
다음 슬라이드에서는 이 기준을 바탕으로 직접 인프라 구조를 설계해보겠습니다.
```

``` 스크립트
이제 앞에서 본 기준을 바탕으로 직접 인프라 구조를 설계해보겠습니다.

이번 실습의 목적은 정답을 맞히는 것이 아니라, 주어진 요구사항에 대해 어떤 구조를 선택했고 왜 그렇게 판단했는지를 설명할 수 있도록 하는 데 있습니다.
먼저 요구사항을 정리한 뒤, 아키텍처 패턴을 선택하고, 컴퓨팅, 데이터베이스, 네트워크, 보안, 운영 항목까지 순서대로 정리해보시면 됩니다.
결과물은 완벽한 설계안이 아니라, 서비스 목적에 맞는 합리적인 초안이면 충분합니다.

이 실습을 통해 요구사항을 정의하고, 아키텍처를 설계하며, 인프라 구성 요소를 선정하는 과정을 경험할 수 있습니다.
🔹 Step 1. 요구사항 정의하기
먼저, 시스템이 요구하는 인프라 스펙을 정확하게 정의하는 것이 가장 중요합니다.
이를 위해 아래 요소들을 분석해야 합니다.
📌 예상 사용량(트래픽) 분석
일 평균 접속자 수(DAU, MAU), 동시 접속자 수(CCU) 등을 예측하여 트래픽 규모를 파악합니다.
**트래픽 급증(예: 이벤트, 시즌성 트래픽)**을 고려하여 확장성을 검토합니다.
📌 데이터 처리량 정의
하루 평균 데이터 저장 용량과 읽기/쓰기 트랜잭션을 예측해야 합니다.
데이터가 실시간으로 처리되어야 하는지, 배치 처리로도 충분한지 판단해야 합니다.
📌 보안 요구사항 설정
민감한 사용자 정보, 결제 데이터 등이 포함될 경우 암호화, 접근 제어, 규정 준수(예: GDPR, ISO 27001) 등을 고려해야 합니다.
📌 가용성 및 복구 계획 수립
**서비스 중단 허용 시간(SLA, RTO/RPO 기준)**을 정해야 합니다.
단일 장애점(SPOF)을 제거하기 위한 이중화 및 재해 복구 전략을 고려합니다.

🔹 Step 2. 아키텍처 설계
다음으로, 인프라의 전체적인 아키텍처를 설계합니다.
📌 클라우드 vs 온프레미스 선택
클라우드(AWS, GCP, Azure)
유연한 확장성, 운영 부담 감소, 초기 투자 비용 절감
온프레미스(자체 서버 구축)
특정 보안 요건(예: 금융권, 공공기관), 규정 준수 요구
📌 단일 리전 vs 다중 리전 구성
단일 리전 배포
운영이 단순하며 비용 절감 가능 (초기 단계 프로젝트에 적합)
다중 리전 배포
글로벌 서비스 지원, 장애 발생 시 복구 속도 향상 (대기업, 미션 크리티컬 서비스에 적합)
이 과정에서 확장성과 운영 편의성을 고려하여 적절한 배포 방식을 선택해야 합니다.

🔹 Step 3. 인프라 구성 요소 선정
📌 컴퓨팅 리소스 선택 (EC2 vs 컨테이너 vs 서버리스)
EC2 (가상 머신 기반):
전통적인 방식, 직접 OS 및 환경 설정 가능
컨테이너(Kubernetes, ECS, EKS):
애플리케이션 이동성이 뛰어나며 DevOps 환경에 적합
서버리스(AWS Lambda, GCP Cloud Functions):
이벤트 기반, 자동 확장 가능, 짧은 실행 시간 서비스에 최적
📌 데이터 저장소 선택
관계형 데이터베이스(RDS, PostgreSQL, MySQL) → 트랜잭션이 중요한 서비스
NoSQL (DynamoDB, MongoDB) → 빠른 읽기/쓰기, 비정형 데이터 저장
파일 저장소 (S3, EFS, Google Cloud Storage) → 정적 파일, 로그 저장
이 단계에서는 애플리케이션 특성에 맞는 최적의 스토리지 솔루션을 선택해야 합니다.

🔹 Step 4. 네트워크 및 보안 설계
📌 네트워크 아키텍처 구성
서브넷 및 VPC(Virtual Private Cloud) 설정
퍼블릭 서브넷: 외부 서비스(웹 서버)
프라이빗 서브넷: 내부 데이터베이스, 캐시 서버
📌 보안 강화
방화벽(Security Group, NACL) 설정 → 네트워크 접근 제한
VPN 또는 전용선 연결(Direct Connect, Cloud VPN) → 사내 네트워크와 클라우드 간의 안전한 연결
IAM(Identity & Access Management) 정책 적용 → 최소 권한 원칙(Least Privilege) 준수
이 단계에서 보안이 취약한 구조를 방지하고, 네트워크 트래픽을 안전하게 관리하는 전략이 필요합니다.

🔹 Step 5. 운영 및 최적화
📌 모니터링 및 로깅 시스템 구축
AWS CloudWatch, Prometheus, ELK(Stack) 등을 활용하여 실시간 모니터링 및 로그 분석
시스템 장애 감지 및 대응 자동화 (Auto Healing, 알림 시스템 구축)
📌 장애 대응 및 재해 복구 시나리오 마련
장애 감지 후 자동 복구(Auto Recovery, Auto Scaling 활용)
데이터 백업 및 복구 전략(Backup & Restore, Multi-AZ, Cross-Region Replication)
이 단계에서는 실시간 운영 및 장애 대응을 고려한 최적의 환경을 구성해야 합니다.

🔹 결론
이번 실습을 통해 요구사항 정의부터 네트워크, 보안, 운영까지 인프라 설계의 전반적인 과정을 경험해보았습니다.
실제 프로젝트에서는 각 요소 간의 균형을 맞추고, 비용 효율성과 성능 최적화를 고려하는 것이 핵심입니다.
```

### 2) 로그인 인증 설계
#### Slide - 로그인 인증: 기본 개념
✔ 인증(Authentication)
사용자의 신원을 검증하는 과정 (일반적으로 ID와 PW 사용)
추가적인 인증 방법: OTP, 생체인증, 패스워드리스 로그인

✔ 인가(Authorization)
인증된 사용자에게 적절한 권한을 부여
접근 가능한 리소스 및 기능 설정 (RBAC & ABAC 모델 적용 가능)

✔ 세션 기반 인증 (Session-Based Authentication)
사용자가 로그인한 이후 세션 ID를 부여하고 이를 서버에서 관리
일정 시간 동안 로그인 상태 유지 (타임아웃 설정 가능)
보안 고려사항: 세션 하이재킹 방지, 세션 갱신 및 만료 정책 적용

✔ 토큰 기반 인증 (Token-Based Authentication)
로그인 시 JWT 토큰등을 발급하여 클라이언트가 저장
서버에서 세션을 유지할 필요 없이, API 요청 시 토큰을 전달하여 인증 수행
장점: 서버 부하 감소(Stateless), 분산 시스템에 적합
보안 고려사항: 토큰 탈취 방지, 만료 및 갱신 정책 적용

``` 스크립트
이번 슬라이드에서는 로그인 인증의 핵심 개념과 주요 요소를 설명드리겠습니다.
로그인 인증은 사용자의 신원을 확인하고, 적절한 권한을 부여하여 시스템 보안을 강화하는 과정입니다.
이를 통해 인증된 사용자만 특정 기능과 데이터에 접근할 수 있도록 제한할 수 있습니다.
로그인 인증의 주요 요소는 크게 네 가지로 나뉩니다.

1️⃣ 인증(Authentication) – 사용자의 신원 확인
먼저, 인증(Authentication) 과정입니다.
이는 사용자가 주장하는 신원이 실제로 올바른지 검증하는 단계입니다.
일반적으로 ID와 비밀번호(PW) 조합이 가장 많이 사용되지만, 보안 강화를 위해 추가적인 인증 방법도 활용됩니다.
OTP(일회용 비밀번호): 사용자의 휴대폰으로 전송되는 코드 입력
생체 인증: 지문, 얼굴 인식 등 고유한 생체 정보를 이용한 인증
패스워드리스 로그인: 이메일 링크, FIDO 기반 인증 등 비밀번호 없이 로그인을 수행하는 방식

2️⃣ 인가(Authorization) – 접근 권한 부여
다음은 인가(Authorization) 단계입니다.
인증이 신원을 확인하는 과정이라면, 인가는 사용자가 어떤 리소스와 기능에 접근할 수 있는지 결정하는 과정입니다.
접근 제어 방식에는 여러 가지가 있습니다.
RBAC(Role-Based Access Control): 역할(Role) 기반 권한 관리.
예: 일반 사용자와 관리자 계정의 접근 권한 차이
ABAC(Attribute-Based Access Control): 속성(Attribute) 기반 권한 관리.
예: 특정 부서의 직원만 내부 문서 접근 가능
이처럼, 사용자의 역할과 속성을 기반으로 필요한 최소한의 권한을 부여하는 것이 보안의 핵심 원칙입니다.

3️⃣ 세션 기반 인증 (Session-Based Authentication)
세 번째는 세션(Session) 기반 인증입니다.
사용자가 로그인하면 서버에서 세션을 생성하고, 세션 ID를 부여하여 사용자의 인증 상태를 유지합니다.
이후 사용자는 세션 ID를 포함한 요청을 통해 로그인 상태를 유지한 채 서비스를 이용할 수 있습니다.
하지만 세션 기반 인증은 서버가 세션을 관리해야 하므로 트래픽이 많아지면 부하가 증가하는 단점이 있습니다.
이를 보완하기 위해 세션 타임아웃 설정, 세션 ID 갱신, HTTPS 사용 등의 보안 조치가 필요합니다.

4️⃣ 토큰 기반 인증 (Token-Based Authentication)
마지막은 토큰(Token) 기반 인증입니다.
이 방식은 로그인 시 서버가 JWT(JSON Web Token)과 같은 토큰을 생성하여 클라이언트에 전달하는 방식입니다.
이후 사용자는 서버에 요청을 보낼 때마다 토큰을 포함하여 인증을 수행합니다.
🔹 토큰 기반 인증의 장점
✅ Stateless(무상태성) – 서버가 인증 정보를 별도로 저장할 필요 없음
✅ 확장성 – 마이크로서비스 및 분산 시스템에서 효과적
✅ 다중 플랫폼 지원 – 모바일, 웹, API 서비스에서 동일한 방식으로 인증 가능
하지만 토큰이 탈취될 경우 보안 위험이 커질 수 있기 때문에,
🔒 토큰의 만료 시간 설정, 보안 저장(예: HttpOnly 쿠키), 리프레시 토큰 사용 등의 보안 조치가 필요합니다.

📌 결론
✅ 인증과 인가의 개념을 명확히 구분해야 한다.
✅ 세션 기반 인증과 토큰 기반 인증은 각기 장점과 단점이 있다.
✅ 보안성과 확장성을 고려하여 적절한 인증 방식을 선택해야 한다.
이제 다음 단계에서는 이러한 로그인 인증 방식들이 어떻게 변화해왔는지를 살펴보겠습니다. 🚀
```

로그인 인증 방식의 변화

``` 스크립트
🔹 1세대 인증 – 개별 서비스별 인증 (Centralized Authentication)
먼저 1세대 인증 방식입니다.
이 방식은 각 서비스별로 개별적인 계정을 생성하고, 아이디(ID)와 비밀번호(PW) 기반으로 인증을 수행하는 전통적인 방식입니다.
✅ 특징
사용자가 각 서비스마다 별도로 가입하고 계정을 관리해야 합니다.
서비스 제공자가 사용자의 인증 정보를 중앙 서버에 저장합니다.
로그인 시 아이디와 비밀번호를 입력하여 검증하는 방식입니다.
✅ 예시
일반적인 웹사이트 회원가입 및 로그인 (예: 이메일 기반 로그인)
✅ 장점
구현이 단순하고 익숙한 방식이기 때문에 빠르게 적용할 수 있습니다.
✅ 단점
해킹 위험이 크다: 중앙 서버에 보관된 계정 정보가 해킹될 경우, 대규모 유출이 발생할 수 있습니다.
사용자 불편: 각 서비스마다 별도의 계정을 생성하고 관리해야 하는 번거로움이 있습니다.

🔹 2세대 인증 – ID 공급자 기반 인증 (Federated Authentication)
다음은 2세대 인증 방식입니다.
이 방식은 OAuth와 같은 프로토콜을 활용하여 제3자가 인증을 대신 처리하는 방식입니다.
우리가 흔히 사용하는 **소셜 로그인(Google, Facebook, Apple, Kakao 등)**이 대표적인 사례입니다.
✅ 특징
여전히 중앙화된 방식이지만, 서비스 제공자가 아닌 제3자(ID 공급자, Identity Provider)가 인증을 담당합니다.
사용자 정보는 구글, 메타(Facebook), 카카오 등의 ID 공급자 서버에 저장됩니다.
사용자는 하나의 계정으로 여러 서비스에 로그인할 수 있습니다.
✅ 예시
구글 로그인, 페이스북 로그인, 애플 로그인, 카카오 로그인 등
✅ 장점
사용자 편의성 향상: 하나의 계정으로 여러 서비스에 로그인할 수 있어 비밀번호 관리 부담이 줄어듭니다.
서비스 간 연동 가능: OAuth 기반으로 다양한 서비스와의 싱글 사인온(SSO, Single Sign-On)이 가능합니다.
✅ 단점
보안 위험: 제3자의 서버가 해킹되면 연결된 모든 서비스 계정이 위험해질 수 있습니다.
벤더 종속성: 특정 플랫폼(구글, 메타 등)에 사용자 계정이 종속되는 문제가 있습니다.
✅ 최근 사례 – 소셜 로그인 계정 해킹 문제
최근 구글, 페이스북 등의 계정이 해킹되면서 중요한 개인정보가 탈취되고 악용되는 사례가 증가하고 있습니다.
특히 연예인, 정치인 등 유명인의 소셜 계정이 해킹되어 사적인 정보가 유출되거나,
피싱 공격을 통해 금융 계정까지 탈취당하는 등의 보안 사고가 발생하고 있습니다.
이러한 문제를 해결하기 위해 더 안전한 인증 방식이 필요하게 되었습니다.
그 해답이 바로 3세대 인증 방식, 자기주권신원(SSI, Self-Sovereign Identity) 기반 인증입니다.

🔹 3세대 인증 – 탈중앙화 인증 (Decentralized Authentication)
마지막으로, 3세대 인증 방식입니다.
이 방식은 탈중앙화(Decentralized)된 구조를 기반으로, 사용자가 직접 자신의 인증 정보를 소유하는 방식입니다.
✅ 특징
블록체인 및 분산 신원증명(SSI, Self-Sovereign Identity) 기술을 활용하여 중앙 서버가 필요하지 않습니다.
인증서(VC, Verifiable Credential)와 개인 키(Private Key)를 사용자가 직접 관리합니다.
기존 중앙화된 ID 공급자(Google, Facebook 등)의 개입 없이 사용자가 직접 자신의 신원을 검증할 수 있습니다.
✅ 예시
DID(Decentralized Identifier) 기반 인증 시스템
블록체인 기반 로그인 서비스 (예: Microsoft Entra Verified ID, Polygon ID, Sovrin 등)
✅ 장점
개인 정보 보호 강화: 사용자가 자신의 신원 정보를 직접 관리하므로, 해킹에 의한 대규모 정보 유출 위험이 없습니다.
중앙 서버 불필요: 기존처럼 제3자의 서버에 의존할 필요가 없어 벤더 종속성이 없습니다.
프라이버시 보호: 사용자 정보가 불필요하게 공유되지 않고, 필요한 정보만 선택적으로 제공할 수 있습니다.
✅ 단점
초기 도입이 어려움: 기존 서비스들과의 연동을 위해 표준화 및 기술 개발이 필요합니다.
사용자 경험 개선 필요: 일반 사용자가 직접 인증 정보를 관리해야 하므로, 초기 설정 과정이 다소 복잡할 수 있습니다.

🔹 결론 – 인증 방식의 진화 방향
✅ 1세대(중앙화된 개별 인증) → 보안 문제 및 사용자 불편
✅ 2세대(ID 공급자 기반 인증) → 편리하지만, 보안 위협과 플랫폼 종속 문제
✅ 3세대(탈중앙화 인증, SSI 기반) → 사용자 주권 강화, 개인정보 보호 강화
결국, 인증 방식은 보안성과 사용자 편의성을 모두 고려하여 발전하고 있으며,
미래에는 자기주권신원(SSI) 기반의 탈중앙화 인증이 핵심 트렌드가 될 가능성이 높습니다.
이제, 이러한 인증 방식을 고려할 때 실제 서비스에 적용하기 위한 설계 방식을 살펴보겠습니다. 🚀


```
---
#### Slide - 로그인 인증 설계의 핵심 요소
✅ 보안
안전한 인증 절차, 암호화, 다단계 인증(MFA), 전송 보호 체계 적용

✅ 인증 서버
로그인 요청 처리, 세션 및 토큰 발급, 인증 흐름 관리

``` 스크립트

1️⃣ 비밀번호 보안 – 안전한 저장 방식 적용
첫째, **비밀번호 해싱(Hashing)**입니다.
사용자의 비밀번호는 절대로 평문(Plain Text)으로 저장해서는 안 됩니다.
반드시 안전한 해시 알고리즘을 적용해야 하며, 대표적인 알고리즘으로 Bcrypt, Argon2, PBKDF2가 있습니다.
이러한 알고리즘들은 계산 비용이 높아 **브루트포스 공격(Brute-force Attack)**에 대한 저항성이 강합니다.
또한, 솔트(Salt) 값을 추가하여 동일한 비밀번호라도 해시 값이 다르게 저장되도록 해야 합니다.

2️⃣ 데이터 전송 보안 – SSL/TLS 암호화 적용
둘째, 데이터 전송 시 보안 강화입니다.
클라이언트와 서버 간의 모든 데이터 전송은 SSL/TLS 암호화를 적용하여 보호해야 합니다.
이를 위해 HTTPS 프로토콜을 사용하고, 최신 TLS(Transport Layer Security) 버전을 적용해야 합니다.
이렇게 하면 **중간자 공격(Man-in-the-Middle Attack, MITM)**을 방지할 수 있으며,
데이터의 기밀성(Confidentiality)과 무결성(Integrity)을 보장할 수 있습니다.

3️⃣ 브루트포스 공격 방지 – 로그인 시도 제한 및 CAPTCHA 적용
셋째, 브루트포스 공격 방지입니다.
공격자가 반복적으로 무차별 대입(Brute-force)하여 계정을 탈취하는 것을 방지하기 위해
다음과 같은 보안 조치를 적용할 수 있습니다.
로그인 시도 제한:
일정 횟수 이상 로그인에 실패하면 일시적으로 계정 잠금 또는 지연 적용
점진적 지연(Increasing Delay):
로그인 실패 시 다음 시도까지의 대기 시간을 점진적으로 증가
CAPTCHA 적용:
자동화된 로그인 시도를 차단하여 봇(Bot) 공격을 방어
이러한 조치를 통해 불법적인 접근을 사전에 차단할 수 있습니다.

4️⃣ 다중 인증(MFA) – 비밀번호 유출 시 추가 방어선 제공
넷째, 다중 인증(MFA, Multi-Factor Authentication) 적용입니다.
비밀번호만으로는 보안이 충분하지 않기 때문에,
추가적인 인증 절차를 통해 보안성을 더욱 강화할 수 있습니다.
대표적인 MFA 방식은 다음과 같습니다.
OTP(One-Time Password):
Google Authenticator 또는 SMS 인증 코드 활용
생체 인증(Biometric Authentication):
지문, 얼굴 인식(FIDO2, WebAuthn 기반)
하드웨어 토큰(Security Key):
YubiKey, Titan Security Key 같은 물리적 인증 장치 사용
이러한 방식은 비밀번호가 유출되더라도 추가적인 방어선을 제공하여
계정 탈취 위험을 크게 줄일 수 있습니다.

5️⃣ 보안 로그 및 모니터링 – 이상 로그인 감지
마지막으로, 로그 및 보안 모니터링(Security Monitoring) 시스템을 구축해야 합니다.
이상 로그인 시도를 탐지하고 빠르게 대응할 수 있도록 로그를 저장하고 분석해야 합니다.
```

#### Slide - 로그인 인증 설계 > 2. 인증 서버(Authentication Server)
인증 서버(Authentication Server)
✅ 인증 서버의 역할
- 사용자 인증 요청 검증
- 세션 및 토큰 발급, 갱신, 폐기
- 접근 제어 및 인증 정책 적용

✅ 인증 서버 설계 고려 사항
- 고가용성(High Availability): 로드 밸런싱, 장애 전환 구조
- 확장성(Scalability): 수평 확장, 캐시 기반 검증
- 보안성(Security): 암호화 통신, 비밀키 관리, 토큰 서명
- 성능 최적화(Performance Optimization): 인증 요청 부하 분산, 응답 지연 최소화

✅ 상태 관리 방식
- 세션 기반 인증: 서버 중심 상태 관리
- 토큰 기반 인증: 클라이언트 토큰 기반 인증 처리
- 서비스 구조와 운영 방식에 따른 적절한 방식 선택

``` 스크립트
이제 로그인 인증 시스템의 핵심 요소 중 하나인 **인증 서버(Authentication Server)**에 대해 살펴보겠습니다.
인증 서버는 사용자의 인증 요청을 처리하고, 세션 및 토큰을 발급 및 관리하는 역할을 수행합니다.
즉, 사용자가 로그인할 때 입력된 자격 증명이 올바른지 확인하고, 성공 시 인증 정보를 발급합니다.

1️⃣ 인증 서버의 주요 역할
✅ 사용자 인증 요청 처리
사용자의 ID, 비밀번호 또는 OAuth/Social Login 요청을 검증
Multi-Factor Authentication(MFA) 적용 시 추가 인증 절차 수행
✅ 세션 및 토큰 발급
로그인 성공 시 세션 ID 또는 JWT(JSON Web Token) 발급
OAuth 2.0 또는 OpenID Connect를 활용한 인증 토큰 관리
✅ 보안 및 접근 제어 정책 적용
비밀번호 해싱, SSL/TLS 암호화 적용
인증 정보 유효성 검사 및 만료된 세션 자동 정리
이처럼 인증 서버는 로그인 인증 시스템의 보안성과 사용자 경험을 모두 결정하는 중요한 요소입니다.

2️⃣ 인증 서버 설계 시 고려해야 할 사항
📌 1. 고가용성(High Availability) – 중단 없는 인증 서비스 제공
로드 밸런싱(Load Balancing): 여러 개의 인증 서버를 운영하여 부하를 분산
Failover 구조: 인증 서버 장애 발생 시 다른 서버로 자동 전환
📌 2. 확장성(Scalability) – 증가하는 사용자 요청 대응
수평 확장(Scale-out) 구조 설계: 필요 시 인증 서버 개수를 유연하게 증가
캐싱(Cache) 적용: Redis, Memcached 등을 활용하여 세션/토큰 검증 속도 향상
📌 3. 보안(Security) – 인증 정보 보호 및 무결성 유지
HTTPS 적용: 모든 인증 요청을 암호화하여 중간자 공격 방지
비밀번호 해싱(Hashing): Bcrypt, Argon2 등을 사용하여 안전하게 저장
토큰 서명(Token Signing): JWT 발급 시 비밀 키를 사용하여 서명
📌 4. 성능 최적화(Performance Optimization) – 빠른 인증 응답 제공
비동기 처리(Asynchronous Processing) 적용으로 인증 속도 향상
토큰 만료 및 재발급 전략(Token Refresh Strategy) 설계
이처럼 인증 서버는 보안과 성능, 확장성을 모두 고려한 설계가 필수적입니다.

3️⃣ 토큰 기반 인증 vs 세션 기반 인증
로그인 인증 방식은 크게 세션 기반 인증과 토큰 기반 인증으로 나뉩니다.
✅ 세션 기반 인증(Session-based Authentication)
서버 측에서 사용자 세션을 유지하며, 요청마다 세션 ID를 검사
장점: 보안성이 높고 세션 제어가 용이
단점: 확장성이 낮으며, 서버 부하 증가
✅ 토큰 기반 인증(Token-based Authentication, 예: JWT)
로그인 성공 시 클라이언트에 토큰을 발급하여 관리
장점: 확장성이 뛰어나고, 마이크로서비스 환경에 적합
단점: 토큰 유효성 검증을 위한 추가적인 관리 필요
```

``` 스크립트
인증 관련 데이터는 사용자의 신원 및 보안과 직결되는 중요한 정보이므로,

1️⃣ 인증 데이터 보호 – 안전한 저장과 관리

✅ 재해 복구 (Disaster Recovery, DR) 계획

✅ 복구 테스트 (Recovery Testing)

데이터 무결성을 검증하고, 복구 소요 시간 최적화

4️⃣ 접근 제어 및 감사 로그 (Access Control & Auditing)
✅ 최소 권한 원칙 적용 (Least Privilege Principle)
데이터베이스 접근 권한을 최소화하여 불필요한 접근을 차단

✅ 모든 인증 관련 변경 사항 로깅 및 모니터링
사용자 로그인 및 인증 관련 모든 이벤트 기록
비정상적인 로그인 시도, 여러 번의 인증 실패 감지 후 자동 알림 및 차단
```

``` 스크립트
이제 로그인 인증 시스템에서 중요한 **세션 및 토큰 관리(Session & Token Management)**에 대해 살펴보겠습니다.
사용자가 로그인한 이후에도 지속적으로 접근을 제어하려면,

📌 효과적인 세션 및 토큰 관리를 위해 고려해야 할 주요 요소는 다음과 같습니다.

1️⃣ 세션 기반 인증 vs. 토큰 기반 인증
✅ 세션 기반 인증 (Session-based Authentication)
서버가 **세션 ID(Session ID)**를 생성하고 클라이언트에 쿠키 형태로 저장
서버 측에서 사용자 상태(Session State)를 유지해야 하므로 **확장성(Scalability)**에 한계가 있음
여러 서버에 분산된 환경에서는 Sticky Session이나 공유 세션 저장소(Redis 등) 필요
✅ 토큰 기반 인증 (Token-based Authentication, JWT, OAuth 등)
서버가 클라이언트에 JWT (JSON Web Token) 또는 OAuth 토큰을 발급
클라이언트는 API 요청 시 토큰을 포함하여 인증
서버가 상태를 유지하지 않으므로 확장성이 뛰어나지만, 보안 정책 적용이 중요
💡 어떤 방식을 선택해야 할까?
소규모 시스템: 세션 기반 인증이 간단하고 효과적
대규모 서비스: 토큰 기반 인증(JWT + OAuth)을 통해 확장성 확보 가능
하이브리드 모델: 로그인 후 첫 요청에 JWT 발급, 이후 API 요청에 사용 가능

2️⃣ 세션 하이재킹 방지를 위한 보안 정책 적용
사용자 세션이 공격자에게 탈취되지 않도록 철저한 보안 정책이 필요합니다.
✅ 세션 고정 공격(Session Fixation) 방지
사용자가 인증에 성공하면 새로운 세션 ID를 발급하여 기존 세션 ID를 무효화
이를 통해 공격자가 사전에 세션 ID를 설정해두는 Session Fixation Attack을 차단
✅ 안전한 쿠키 설정 (Secure Cookie Configuration)
Secure: HTTPS 환경에서만 쿠키 전송
HttpOnly: JavaScript에서 쿠키 접근 차단 (XSS 공격 방어)
SameSite: 교차 사이트 요청 방지 (CSRF 공격 방어)
✅ 세션 타임아웃 및 재인증 (Session Timeout & Re-authentication)
**세션 만료 시간(Time-out)**을 설정하여 일정 시간 동안 활동이 없으면 자동 로그아웃
중요 작업 수행 시 재인증 요구 (Re-authentication)
예: 결제, 계정 정보 변경 시 추가 인증 (MFA 적용 가능)
✅ 동시 로그인 제한 (Concurrent Session Control)
동일한 계정으로 동시에 여러 개의 세션 유지 제한 가능
보안이 중요한 서비스에서는 하나의 세션만 허용하고 기존 세션을 종료

3️⃣ 분산 세션 저장소 및 확장성 고려
대규모 시스템에서는 여러 서버에서 세션을 공유해야 하는 상황이 발생합니다.
이를 해결하기 위해 세션 데이터 저장 전략을 고려해야 합니다.
✅ 인메모리 세션 저장소 활용 (Session Store with In-memory Databases)
Redis, Memcached 등 빠른 읽기/쓰기 성능을 제공하는 인메모리 저장소 활용
다중 서버 환경에서 세션 공유(Shared Session Store) 가능
✅ 로드 밸런싱 환경에서의 세션 유지 전략
Sticky Sessions: 특정 사용자의 요청을 동일한 서버로 전달하여 세션 유지
Shared Session Store: 모든 서버가 동일한 세션 저장소를 참조하여 세션 일관성 유지
💡 Redis vs. Traditional Database?
Redis는 빠른 속도와 낮은 지연 시간으로 세션 저장에 적합
전통적인 관계형 DB(MySQL, PostgreSQL)는 세션 데이터 저장에 비효율적일 수 있음

📌 결론 – 안전한 세션 및 토큰 관리를 위한 핵심 원칙
✅ 세션 기반 vs. 토큰 기반 인증을 상황에 맞게 선택
✅ 세션 하이재킹 방지 정책 적용 (안전한 쿠키, 세션 고정 공격 방어, 재인증 적용)
✅ 분산 환경에서는 Redis와 같은 공유 세션 저장소 활용하여 확장성 확보
✅ 동시 로그인 제한 및 보안 정책을 통해 계정 도용 방지
📌 이러한 전략을 철저히 적용하면,
사용자 경험을 개선하면서도 강력한 보안을 유지하는 인증 시스템을 설계할 수 있습니다. 🚀
```

``` 스크립트
소셜 로그인을 제공하면 로그인 과정이 단순해지지만, 특정 플랫폼에 종속될 위험이 있음

따라서 추가적인 **다중 인증(MFA)**을 적용하거나, 계정 보안 강화를 유도하는 전략이 필요

2️⃣ 비밀번호 복구 절차 간소화 (Simplified Password Recovery)
✅ 간편한 비밀번호 재설정 방식 제공
이메일을 통한 재설정 링크 발송
OTP(일회용 비밀번호) 기반 재설정
보안 질문 또는 생체인증 활용 (예: 모바일 앱에서 지문/안면 인식)
✅ 보안 강화를 위한 추가 검증 절차 적용
비밀번호 재설정 요청 시 이전 로그인 기록 확인 및 추가 인증 요구
무작위 재설정 요청 방지: 일정 횟수 이상 요청 시 제한 및 경고 알림 제공
새 비밀번호 설정 시 강력한 비밀번호 정책 적용 (예: 최소 12자 이상, 대문자·숫자·특수문자 포함)
💡 사용자 편의 vs. 보안 강화
비밀번호 재설정 과정이 복잡하면 사용자 불편 증가
그러나 너무 단순한 절차는 보안 위험을 초래할 수 있으므로, 적절한 검증 메커니즘 필요

3️⃣ 자동 로그인 옵션 제공 (Auto Login & Persistent Sessions)
✅ 보안 토큰을 통한 자동 로그인 지원
장기적인 세션 유지 기능 적용
브라우저 쿠키 또는 디바이스 인증을 통한 자동 로그인 가능
✅ 보안 리스크 고려 및 대응책 적용
자동 로그인 기능이 활성화된 상태에서 중요 작업 수행 시 추가 인증 요구
예를 들어, 결제나 개인정보 변경 시 추가적인 MFA 적용
자동 로그인 토큰의 유효 기간을 설정하고, 사용자가 직접 관리할 수 있도록 옵션 제공
💡 자동 로그인의 딜레마 – 편리함 vs. 보안
사용자 입장에서는 자동 로그인 기능이 매우 편리
하지만 공용 컴퓨터나 도난당한 디바이스에서 악용될 가능성이 있음
따라서 "이 기기에서 로그인 유지" 옵션을 명확하게 제공하고, 관리 기능을 강화하는 것이 중요

4️⃣ 사용자 인터페이스(UI) 및 사용자 경험 개선 (Optimized UI & UX Design)
✅ 로그인 폼의 직관적 설계
불필요한 입력 필드 최소화
입력 오류 메시지를 명확하게 제공 (예: "비밀번호가 틀렸습니다" 대신 "비밀번호가 일치하지 않습니다. 3회 실패 시 계정이 잠길 수 있습니다.")
✅ 다양한 디바이스 및 브라우저에서의 일관된 경험 제공
모바일, 태블릿, 데스크톱 환경에서 동일한 사용자 경험 유지
다크 모드 지원, 화면 확대 기능 등 접근성(Accessibility) 개선
✅ 로그인 후 계정 보안 점검 유도
"최근 로그인 기록 확인" 기능 제공
사용자 계정에 연결된 기기 목록 확인 및 관리 기능 추가
💡 작은 변화가 큰 사용자 경험 차이를 만든다!
단순한 디자인 개선으로도 사용자의 피로도를 줄일 수 있음
직관적인 UI/UX 설계는 보안 강화를 위한 "사용자의 적극적인 참여"를 유도할 수 있음

📌 결론 – 사용자 경험과 보안의 균형 유지하기
```

#### Slide - 로그인 인증 설계 > 6. 인증 방식(Authentication Methods)
인증 방식(Authentication Methods)
✅ 기본 인증
- ID / Password 기반 인증

✅ 생체인식(Biometric Authentication)
- 지문, 얼굴 인식 등 기기 기반 인증

✅ OTP(One-Time Password)
- SMS, 이메일, 인증 앱 기반 일회용 비밀번호 인증

✅ 추가 인증 방식
- 2단계 인증(2FA): 비밀번호 + OTP 등 다중 요소 조합
- 공개키 기반 인증(PKI): 비대칭 키 기반 보안 인증
- Push 기반 인증: 모바일 앱 승인 방식 인증

✅ 인증 방식 선택 기준
- 보안성, 사용성, 기기 호환성, 운영 환경 고려한 다중 인증(MFA) 적용 검토

``` 스크립트
이제 로그인 인증 시스템에서 활용할 수 있는 다양한 인증 방식에 대해 살펴보겠습니다.
다양한 인증 방식을 지원하면 보안성을 높이면서도 사용자 경험을 개선할 수 있습니다.
각 방식의 장점과 단점을 이해하고, 시스템의 요구사항과 사용자 특성에 맞는 인증 방식을 선택하는 것이 중요합니다.

1️⃣ 기본 인증 (ID & Password Authentication)
✅ 가장 전통적이고 널리 사용되는 인증 방식
사용자가 아이디와 비밀번호를 입력하여 인증 수행
사용자가 익숙하지만, 비밀번호 관리 부담 및 보안 취약점 존재
✅ 보안 리스크 및 보완 방법
비밀번호 재사용 문제: 동일한 비밀번호를 여러 서비스에서 사용할 경우 보안 위협 증가
피싱 공격 위험: 악성 사이트에서 사용자의 비밀번호를 탈취할 가능성 존재
보완책
강력한 비밀번호 정책 적용 (최소 길이, 특수문자 포함 등)
비밀번호 해싱 및 솔트 적용 (bcrypt, Argon2, PBKDF2 사용)
정기적인 비밀번호 변경 유도 (단, 너무 잦은 변경 요구는 사용자의 불편을 초래할 수 있음)
💡 비밀번호 인증만으로는 보안이 완벽하지 않으므로 추가적인 보안 요소 적용이 필요합니다.

2️⃣ 생체인식 인증 (Biometric Authentication)
✅ 사용자의 고유한 생체 정보를 활용한 인증
지문 인식, 얼굴 인식, 홍채 스캔 등
높은 보안성과 편의성을 제공
✅ 장점
사용자가 기억할 필요 없음 → 편리성 증가
생체정보는 복제하기 어려움 → 보안성 강화
✅ 보완책 및 고려사항
생체 정보 저장 방식
로컬 저장 (기기 내 저장) → 지문, 얼굴 데이터가 기기 내에서만 처리됨 (예: Apple Face ID)
서버 저장 → 데이터 유출 시 위험이 커질 수 있음 → FIDO2 및 안전한 암호화 적용 필수
대체 인증 방식 제공
생체 인식 기능이 없는 디바이스에서도 로그인 가능하도록 OTP나 패턴 인증을 함께 지원
💡 편리하지만, 생체 정보 유출 시 복구가 불가능하기 때문에 안전한 저장과 관리가 필수적입니다.

3️⃣ OTP (One-Time Password) – 일회용 비밀번호 인증
✅ 비밀번호 유출 위험을 줄이기 위한 추가 보안 계층
이메일, SMS, 인증 앱을 통해 일회용 비밀번호(OTP) 전송
일반적으로 로그인 또는 중요한 작업(결제, 계정 변경) 시 추가 인증 수단으로 사용


✅ OTP 전송 방식 비교

방식	특징	보안성
SMS OTP	사용자가 가장 익숙한 방식, 별도 앱 불필요	SIM 스와핑 공격 취약
이메일 OTP	등록된 이메일을 통해 전송	이메일 계정 해킹 시 위험
TOTP (Time-based OTP, 인증 앱)	Google Authenticator, Authy 등 인증 앱 사용	높은 보안성, 인터넷 연결 불필요

💡 SMS OTP는 편리하지만, SIM 스와핑 공격 등에 취약하므로 가능하면 인증 앱(TOTP) 사용을 권장합니다.

4️⃣ 추가 인증 방식 (Advanced Authentication Methods)
✅ 2단계 인증(2FA, Two-Factor Authentication)

비밀번호 + 추가 인증 요소(OTP, 생체인식 등) 조합
피싱, 계정 탈취, 비밀번호 유출 방지에 효과적
✅ 공개키 기반 인증(PKI, Public Key Infrastructure)

비대칭 암호화(공개키, 개인키)를 활용한 인증 방식
인증서 기반 접근(예: 기업용 VPN, 전자서명)
높은 보안성을 제공하지만, 초기 설정이 복잡할 수 있음
✅ Push 기반 인증

사용자의 모바일 기기로 푸시 알림을 보내고, 승인/거부 버튼 클릭으로 인증
사용자 경험(UX) 개선 효과 → OTP 입력 없이도 간편하게 인증 가능
단, 사용자의 기기가 도난당할 경우 위험 존재
💡 다중 인증(MFA)을 적극 활용하여 보안성을 극대화하는 것이 중요합니다.

📌 결론 – 인증 방식 선택 시 고려할 요소
✅ 보안성과 사용자 경험의 균형 유지

편리한 로그인 경험과 높은 보안성을 동시에 만족시키는 방식 선택
✅ 단일 인증 방식보다 다중 인증(MFA) 활용 권장

ID/PW + OTP, 생체인식 + PIN 등 다양한 인증 방식 조합 적용
✅ 시스템 환경과 사용자 요구사항에 맞는 방식 선택

기업 내부 시스템 vs. 일반 소비자용 서비스 → 인증 방식의 차별화 필요
📌 "완벽한 인증 방식은 없습니다. 중요한 것은 사용자의 편의성과 보안을 조화롭게 설계하는 것입니다."
🚀 최신 보안 트렌드를 반영하고, 지속적인 보안 업데이트를 통해 안전한 인증 시스템을 구축해야 합니다.
```

#### Slide - 로그인 인증 설계 > 7. 확장성(Scalability)
확장성(Scalability)
✅ 로드 밸런싱(Load Balancing)

- 수직 확장(Vertical Scaling): 개별 서버 자원 증설

✅ 확장형 인증 아키텍처
- 세션 클러스터링, 토큰 기반 인증, 비동기 처리 구조 검토
- 사용자 증가에 대응 가능한 인증 구조 설계

``` 스크립트
로그인 인증은 사용자가 몰리는 순간 가장 먼저 병목이 생길 수 있는 영역입니다.
그래서 초기 설계 단계에서부터 확장성을 고려해야 합니다.

핵심은 네 가지입니다.
로드 밸런싱으로 인증 요청을 분산하고, 캐싱으로 반복 검증 비용을 줄이며, 필요할 경우 수평 확장 구조를 준비해야 합니다.
또한 세션 클러스터링이나 토큰 기반 인증 같은 구조를 통해 여러 서버 환경에서도 일관된 인증 처리가 가능해야 합니다.

즉, 확장성은 서버를 많이 두는 문제가 아니라 인증 흐름이 증가하는 트래픽을 자연스럽게 흡수할 수 있는 구조를 만드는 문제입니다.
다음 슬라이드에서는 이러한 인증 요청이 외부에서 들어올 때 첫 관문이 되는 API 게이트웨이를 보겠습니다.
```

#### Slide - 로그인 인증 설계 > 8. API 게이트웨이(API Gateway)
API 게이트웨이(API Gateway)
✅ API 게이트웨이의 역할
- 외부 요청의 진입 지점 및 인증 처리 계층
- 외부와 내부 서비스 간 인터페이스 제공

✅ 요청 제어
- Rate Limiting, Quota, Throttling 적용
- 악성 트래픽 및 과도한 요청 방지

✅ 모니터링 및 로깅
- 인증 요청 추적, 실시간 모니터링, 감사 로그 관리
- 이상 패턴 탐지 및 대응 체계 운영

✅ 보안 정책 강화
- JWT, OAuth 기반 요청 검증
- API 키 관리, 접근 제어, DDoS 대응

✅ 마이크로서비스 아키텍처(MSA)에서의 활용
- 서비스 라우팅, 통합 인증, 중앙 정책 적용

``` 스크립트
API 게이트웨이는 외부 요청이 내부 인증 시스템으로 들어오기 전에 거치는 첫 번째 관문입니다.

이 계층에서는 요청을 단순히 전달하는 것이 아니라, 과도한 요청을 제한하고, 인증 여부를 확인하고, 모든 요청을 추적할 수 있어야 합니다.
그래서 Rate Limiting, Quota, Throttling 같은 요청 제어 정책과 로그, 모니터링, 접근 제어 정책이 함께 필요합니다.
```

✅ 보안 및 세션 관리

``` 스크립트
✔️ 자동 세션 관리 및 토큰 갱신
```

1️⃣ 변경 사항 추적 → 누가, 언제, 무엇을 왜 변경했는지 기록
2️⃣ 버전 관리 → 특정 시점 복원 및 안정적 배포 기준 확보
3️⃣ 협업 지원 → 동시 작업 충돌 최소화 및 산출물 일관성 유지
4️⃣ 품질 향상 → 리뷰, 테스트, 배포 자동화와 연계 가능

📌 형상 관리와 버전 관리의 관계
- 형상 관리(SCM): 개발 전 과정의 산출물과 변경 이력 관리
- 버전 관리(VCS): 형상 관리의 하위 영역으로 파일 버전과 변경 내역 추적
- Git: 대표적인 분산 버전 관리 시스템(DVCS)

``` 스크립트

기획서, 설계서, 설정 파일, 배포 스크립트처럼 서비스 개발 과정에서 만들어지는 모든 산출물을 함께 관리하는 개념으로 이해하시면 됩니다.

여기서 버전 관리는 형상 관리의 한 부분입니다.
그리고 Git은 그 버전 관리를 실제로 수행하는 대표적인 도구라고 보시면 됩니다.
다음 슬라이드에서는 버전 관리와 Git의 역할을 조금 더 직접적으로 연결해서 보겠습니다.
```

``` 스크립트
정리하면, 버전 관리는 원칙이고 Git은 그 원칙을 실무에서 구현하는 도구입니다.
```

#### Slide - Git 브랜치 전략 (구조적 브랜칭 모델)
구조적 브랜칭 모델(Structured Branching Model)
✅ 적용 대상
- 대규모 프로젝트, 장기 개발, 다단계 검증이 필요한 환경

✅ 주요 브랜치 구성
- `main`: 운영 기준 브랜치
- `develop`: 통합 개발 브랜치
- `feature/*`: 기능 개발 브랜치
- `release/*`: 배포 전 점검 브랜치
- `hotfix/*`: 긴급 수정 브랜치

✅ 특징
- 개발, 테스트, 릴리스, 운영의 단계별 분리 가능
- 안정성은 높지만 브랜치 운영 복잡도 증가

``` 스크립트

구조적 브랜칭 모델은 역할이 분명한 여러 브랜치를 두는 방식입니다.
`main`, `develop`, `feature`, `release`, `hotfix`처럼 단계별 브랜치를 분리해 운영하기 때문에, 대규모 프로젝트나 검증 단계가 많은 환경에 적합합니다.

장점은 안정성과 관리 기준이 명확하다는 점이고, 단점은 브랜치 수가 많아질수록 운영 복잡도가 높아진다는 점입니다.
다음 슬라이드에서는 더 단순하고 빠른 운영을 위한 브랜치 전략을 보겠습니다.
```

#### Slide - Git 브랜치 전략 (기능 중심 브랜칭, 트렁크 기반)
기능 중심 브랜칭(Feature-Driven Branching)
✅ 특징
- `main` 또는 `develop`에서 기능별 브랜치 분기

트렁크 기반 개발(Trunk-Based Development)
✅ 특징
- 긴 브랜치 운영을 최소화하고 짧은 주기로 통합
- 작은 단위 커밋과 빠른 병합 지향
- 자동화된 테스트와 CI/CD 전제 필요

브랜치 전략 선택 기준
- 팀 규모, 배포 주기, 테스트 자동화 수준 고려
- 2~3인 MVP 팀은 단순한 브랜치 전략이 운영 효율에 유리

``` 스크립트
모든 프로젝트가 구조적 브랜칭 모델을 써야 하는 것은 아닙니다.
배포 주기가 짧고 팀 규모가 작다면 더 단순한 전략이 오히려 효율적일 수 있습니다.

어떤 전략이 맞는지는 팀 규모, 배포 빈도, 테스트 자동화 수준에 따라 달라집니다.
```
